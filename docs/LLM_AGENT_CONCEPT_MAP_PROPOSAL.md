# LLM 與 Agent 概念地圖：教材架構建議

檢視日期：2026-11-02。對象：目前「大語言模型學習地圖」網站，以及 wanghao-SunSky/cs329z-chinese 的 `8cfcf5a4047f32270e07d5e60fcb98205de37fc0` 版本。

本文件是教材與介面的設計建議；這次尚未改動網站頁面。已檢視中文教材 19 講的章節結構，重點閱讀 Agent 基礎、LLM、RAG、工具、框架、Context、Memory、多 Agent，以及資料、評測、安全的相關段落；另讀 README、課程指南、編寫說明與 HW1 的分階段設計。未執行該倉庫的程式與作業，也未逐項驗證所有數值、公式或論文解讀。

## 1. 判斷：目前需要的是「關係」，不只是更多名詞

現在的查閱目錄已能回答「這個詞是什麼」，首頁六站也提供了閱讀順序。但學生還需要第三種幫助：在一張圖裡看見「它位於哪裡、和誰相連、負責哪一段工作」。

例如，現有 `concepts/overview.html` 是「提出任務 → 準備資訊 → 處理與核對 → 呈現結果」四步流程。方向清楚，但第三步同時容納模型、Agent 和工具，學生仍不容易分辨誰決定、誰執行、結果怎麼回來。

建議新增一個可展開的概念全圖，配合一個具體任務流程。兩張圖使用相同名詞、相同案例。六站課程繼續負責學習順序，概念圖負責位置與關係。

## 2. 如何使用這份 GitHub 教材

這份教材很適合當教師備課資料：它把模型之外的工具、記憶、編排、資料、評測和安全放在同一套系統觀裡。Stanford 官方課程也把 compound systems、LLM pipelines 與 autonomous agents 放在工程脈絡中討論，而不只介紹單一模型。[中文教材 README](https://github.com/wanghao-SunSky/cs329z-chinese/blob/main/README.md)、[Stanford CS329Z](https://cs329z.stanford.edu/)

但它設定的讀者是有 Python 與 API 基礎的開發者。你的學生約六至七成不熟悉這個領域，不適合直接沿用它的術語密度、數學起點和完整作業要求。

來源也要分清楚：這是獨立整理的中文自學材料，並非官方翻譯。作者說明第 1–10 講已有課件文字，第 11–19 講含依課表與閱讀清單延伸的內容，第 16 講的架構回顧屬擴充；編寫說明亦列出尚待修正的公式與 DPO 等問題。因此，適合借用問題意識與內容結構，採用個別技術敘述時仍應核對原始資料。[編寫說明](https://github.com/wanghao-SunSky/cs329z-chinese/blob/main/docs/editorial-notes.md)

## 3. 第一張圖：六個問題組成的概念地圖

主題用「以 LLM 為核心的 AI 助手」。AI 是更大的領域，LLM 是其中一類模型；本課聚焦使用 LLM 的應用系統。不要把 AI、LLM、RAG、Agent 畫成四個必然依序升級的版本。

第一眼顯示六個白話問題，每一支只露出一至兩個核心名詞。點擊某一支才展開其細節；一次展開一支，避免全圖變成密密麻麻的字牆。這些是教學分類，不表示每套系統都要具備所有元件。

| 分支 | 初學者先懂 | 展開後可以看到 | 對應既有頁面 |
| --- | --- | --- | --- |
| 理解與生成：誰產生內容？ | LLM、Token | Tokenizer、Transformer、Attention、MoE、預訓練、微調、LoRA、推論、取樣 | model、tokens、sampling、moe、knowledge |
| 交代任務與資訊：這次要給它什麼？ | Prompt、Context | System Prompt、Context Window、Context Engineering、Compaction | prompt、context、context-engineering |
| 查資料與留記錄：資訊從哪裡來？ | RAG、Memory | 切片、Embedding、索引、關鍵字／向量／混合檢索、本輪工作記憶、跨次記憶 | knowledge、context、context-engineering；記憶專題 |
| 實際執行操作：誰真的去做？ | Tool、API | Tool Calling、Schema、MCP、Computer Use | agent-tools、api |
| 安排下一步：流程由誰決定？ | Workflow、Agent Loop | Harness、Skill、狀態與重試、Multi-agent、Handoff | agent、agent-operation、agent-tools |
| 核對結果與界線：怎麼知道做對了？ | Evals、權限 | 完成條件、測試案例、可觀察的 Trace、Prompt Injection、人員確認、步數／時間／費用限制 | verification、evidence、injection、cost |

這裡有幾組關係應明確畫出：

- Prompt 是 Context 的一部分。Context Engineering 處理的不只一段提示詞，也包含資料、工具回覆、對話與狀態如何被選入這一輪輸入。[Context Engineering 原文](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- RAG 是查找資料後把相關內容帶入生成過程；它可以用在簡單問答，也可以成為 Agent 的工具。不是所有 RAG 都需要 Agent。
- MoE 放在「模型內部」；Multi-agent 放在「多個執行角色如何合作」。兩者所在層次不同。[Switch Transformers](https://arxiv.org/abs/2101.03961)
- Tool Calling 是模型提出操作請求，實際執行與權限判斷由宿主程式處理。MCP 是連接工具、資源等能力的協定，可和既有 API、Tool Calling 一起使用。[MCP 架構規範](https://modelcontextprotocol.io/specification/2025-06-18/architecture)
- 工作流程可以預先寫定；Agent 可以在系統允許的範圍內依結果選擇下一個動作。兩種方式能混合使用。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Graphic、圖表和 Generative UI 放在輸出／互動介面的位置。它們不是與 LLM、Agent 同一層的模型類型。

「查資料」與「留記錄」會有交集，例如檢索以前的工作紀錄；分類只是幫助定位，不強迫每個名詞只能出現一次。補充關係用「也用於……」連結呈現，不重複建立兩份定義。

## 4. 第二張圖：同一個任務如何跑完

全站沿用「整理活動報名資料，核對人數，再製作圖表」這個例子。學生已理解任務，就能把注意力放在新概念。

基本流程：

1. **定義任務與完成條件。** 例如要依場次統計有效報名人數，排除取消紀錄，圖表要標出資料日期。
2. **準備 Context。** 放入任務、當次報名表、統計規則；如有需要，再查詢活動規定或取用已保存的偏好。
3. **LLM 判斷下一步。** 例如提出「用計算工具按場次統計」的請求。
4. **宿主程式檢查。** 核對工具名稱、參數和權限；需要確認的動作先取得確認。
5. **工具實際執行。** 讀取資料、計算、製圖，回傳結果或錯誤。
6. **將結果帶回 Context 並核對。** 總數是否一致？是否漏掉一個場次？如果資料缺漏，可再查資料或詢問使用者。
7. **達標後交付。** 提供圖表、摘要與必要依據；反覆失敗或超出限制時停止，不無限循環。

圖上必須有一條「工具結果 → 下一輪模型輸入」的回箭頭。否則學生看到的只是單向流程，無法理解 Loop 的用途。

這是簡化的工具循環示意，不表示每次回答都要呼叫工具；LLM 也可以直接回答或詢問。權限檢查要畫在執行之前，驗證結果則在執行之後。Trace 指可觀察的請求、回覆與操作紀錄，不宣稱能讀取模型內部完整思考。

另一個小比較可放在 Agent 閱讀頁：同樣整理報名表，Workflow 使用預先設計的路徑（讀表 → 統計 → 製圖）；Agent 在允許的工具範圍內，依實際結果決定是否補查、重算或詢問。先問任務是否真的需要這種彈性，再介紹更複雜的系統。

## 5. 混合程度的學生，使用同一份教材的三層深度

### 第一層：先完成白話主線

進入一個主題，先看「一個問題、一句解釋、一張圖、一個例子」。核心內容不依賴 Python，也不要求先理解 Transformer 數學。

例如 RAG 的開場可以是：「助手不知道活動的最新規定時，先找出相關文件，把查到的內容放進這次輸入，再整理回答。」接著畫三個位置：文件、查到的片段、模型回答。

### 第二層：點開原理與差異

學生有疑問時才展開檢索方式、記憶如何取回、Schema 是什麼、MoE 與多 Agent 有什麼不同等內容。保留現有長文與圖解，讓它們變成可抵達的深入閱讀，而不是從首頁拿掉。

### 第三層：用挑戰題服務熟悉者

每個主題加一題需要比較或診斷的任務，避免只增加更多名詞：

- RAG：檢索到了過期規定，答案為什麼仍然可能錯？
- 記憶：系統保存了對話，但這輪沒取回，模型能使用嗎？
- 工具：模型要求發送通知，程式應先檢查哪些條件？
- Agent：什麼情況用固定 Workflow 更容易檢查與維護？
- 評測：怎麼驗證「製圖成功」，而不是只相信助手說「已完成」？

這是建議的教學分層，不是由學生比例推算出的時間分配。可先以一個班的試教觀察調整。

## 7. 對目前網站的具體落點

優先完成以下四件事即可，不必再增加一套全站導覽：

1. **擴充整體概念頁。** `concepts/overview.html` 成為概念全圖的主要位置，可切換「有哪些組成／任務怎麼跑」，每個名詞連到現有閱讀頁。首頁與查閱目錄加「看概念全圖」入口，維持三個主要導覽。
2. **補 Agent 的比較圖。** 在現有 Agent 頁加入 Workflow、單次工具呼叫、Agent Loop 的差異，明確標出決策、程式執行與停止點。
3. **補記憶的層次圖。** 分開顯示模型參數、當次 Context、保存的聊天紀錄、外部長期記憶。「保存」與「本輪被取回」是兩個動作。記憶可以存在檔案或資料庫，不限定向量資料庫；認知架構研究也把記憶、動作與決策過程分開處理。[CoALA](https://arxiv.org/abs/2309.02427)
4. **補完成與評測。** 在既有核對頁用報名表例子定義輸入、預期結果、驗證方式、錯誤案例；可觀察執行紀錄放進 Agent 深入閱讀。先建立正確判斷，再介紹 LLM-as-a-Judge 等方法。

保留目前課程進度、實驗、API 設定入口、35 個名詞查閱與舊頁連結；分層只改變一開始顯示多少，所有內容仍可到達。手機版採直向分支，先看六個問題，再點開一支，不靠縮小整張桌面圖閱讀。

### 實作時的驗收問題

- 初學者能否從圖上指出「誰產生請求、誰實際執行」？
- 能否找到 Prompt、Context、RAG、記憶之間的資料關係？
- 能否分辨 MoE 與 Multi-agent 所在的層次？
- 能否解釋 Loop 為什麼回頭，以及什麼時候停止？
- 熟悉者能否在兩次操作內找到深入內容，而非重新讀完六站？
- 小螢幕、鍵盤操作、返回地圖與既有深連結是否正常？
- 概念圖是否仍能讓學生看見完整架構，而不是只剩一個只能逐項翻頁的選單？

以上是教材設計與介面驗收建議，尚未經學生試教；最適合先以 Agent／記憶兩個主題驗證，再擴展到其他內容。
